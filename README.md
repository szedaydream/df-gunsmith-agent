# 改枪顾问 Agent · Delta Force Gunsmith

> 一个**垂直领域 LLM Agent**：描述你的武器和打法，它判断意图、按需联网检索资料、生成一套**带来源标注**的配件方案，然后**自己质检、不合格自动重写**。

不是"套壳调 API"，而是一个有**意图路由、条件检索、规则质检、自动修正、可观测性**的完整应用。
本文档里的所有数字都来自本仓库代码的真实运行记录。

---

## 一、它解决什么问题

游戏改枪咨询有三个具体的坑：

| 坑 | 表现 | 本项目的应对 |
|---|---|---|
| **模型会编造配件** | 一本正经地给出不存在的配件名和数值 | 每条配件**强制标注来源**：`（档案）`/`（搜索资料）`/`（推理）`/`（未核实）` |
| **信息不足时瞎给方案** | 用户只说"帮我改枪"，它直接输出一整套 | 意图判断先抽槽位，**缺关键信息就反问**（`clarify`），不硬答 |
| **输出结构会缺斤少两** | 声称"共 12 个配件槽"但只列了 10 条 | **出厂质检**逐张方案卡校验，不过关**打回重写一次** |

第三点实测有效——质检器真的抓到了这个问题：

```
🧪 质检发现 1 处问题，正在自动修正…
validation_issues: ["声称共 12 个槽但只列了 10 条"]     fix_retried: 1
```

## 二、实测数据

以下是本机真实跑通的记录（模型 `kimi-k3`，Router `kimi-k2.6`）：

| 指标 | 实测值 |
|---|---|
| 输入 | `M4A1，烽火地带，中近距离，预算不限，给我一套配件方案` |
| 意图判断 | `answer` ｜ 抽出 **7 个槽位**：`枪=M4A1 模式=烽火地带 距离=中近 指定配件=无 取向=满改 水平=未知 预算=无` |
| 画像沉淀 | 自动合并为 `{'模式': '烽火地带', '取向': '满改'}`，**跨对话存活** |
| 输出 | **2230 字**，6 个结构段齐全 |
| 质检 | 抓到 1 处不一致 → 自动修正 1 次 → 输出修正版 |
| 耗时 / token | `intent_ms=9163` `total_ms=59316` `prompt_tokens=3673` `completion_tokens=1895` |
| 流式事件 | **1868 个 SSE 事件**（243 个思考分片 + 1620 个正文分片） |

输出片段（注意每条后面的来源标注）：

```
【枪托】M16A4稳定枪托 —— M4A1独家特性，装托腮板后双倍枪托精校上限，后坐力减免是这枪的命门（档案）
【弹匣】45发扩容 —— 聪聪点名30发续航不足，满改必扩（聪聪）
【瞄具】红点/低倍镜 —— 中近距离为主，红点视野干净（推理）
【枪管】长枪管 —— 中距离保伤害衰减和弹速，满改必上（未核实）
```

> 「（档案）」= 命中本地枪械档案；「（聪聪）」= 引用档案收录的实战方案；
> 「（推理）」= 模型在已有事实上推导；「（未核实）」= **模型自己补的、没有依据，明确告诉用户别当准的**。

## 三、领域数据不是手打的：从游戏客户端缓存里提取

`tools/extract_game_cache.py`（449 行）从《三角洲行动》客户端落盘的 HTTP 响应缓存中，提取出**真实的官方数据**：

| 产物 | 内容 | 体积 |
|---|---|---|
| `data/game/guns.json` | 枪械，**含官方真实数值** | 50 KB |
| `data/game/attachments.json` | 配件，含优点 / 缺点 / 数值修正 | 268 KB |
| `data/game/items.json` | 全部道具（枪 + 配件）规范化后的统一字典 | 318 KB |
| `data/game/schemes.json` | 官方社区改枪方案（含改枪码） | 170 KB |
| `data/game/enrichment.json` | 与 `gun_profiles.json` 对照后的「可补全字段」建议 | 11 KB |
| `data/game/extract_report.md` | 本次提取的可读报告 | 5 KB |

脚本对游戏目录**只读**（只 `open(..., 'rb')` 与列目录），并且**启动时与运行时各校验一次输出路径不在游戏目录内**，防止误写。

> **这一层决定了项目的性质：方案里的数值有真实来源，不是模型的记忆。**
> 也正因为如此，`plan_validator` 才敢拿「档案槽位数」去校验模型输出 —— **校验基准是真实数据，不是另一个模型的判断。**

## 四、架构

```
浏览器（templates/chat.html）
  │  POST /send_message  ←→  SSE 流式推送 status / thinking / answer
  ▼
Flask 路由层（app.py）
  │  ① 取会话 id 与用户 id，落盘用户消息
  │  ② 历史增量压缩：超 14 条才压，且只压「上次没压过的」那批（不重复花钱）
  │  ③ 意图判断：clarify / answer / multi / chat
  │  ④ 条件检索：只有 answer/multi 且 need_search 才发起搜索
  │  ⑤ 任务拆分：异构混合才调模型；同类型多枪在代码层直接组（零额外调用）
  │  ⑥ 流式生成，trace 数据落库
  ▼
服务层（services/）
  ├── AIService        调用封装 / 意图 / 拆分 / 画像 / 压缩 / 参数自愈
  ├── SearchService    可插拔适配器：Bocha · Tavily · Null
  └── StorageService   SQLite：消息 · 画像 · 反馈 · 请求日志
  ▼
出厂质检（services/plan_validator.py）
     零 token 的规则校验；不过关 → 把问题清单喂回模型 → 重写一次
```

## 四、六个值得说的设计决策

### 1. 质检用规则，不用模型 —— 省的是真金白银

`plan_validator.py` 的五项检查全是**规则就能判定**的，再花一次 LLM 调用去"检查格式"纯属浪费：

1. 六个必需段落是否齐全
2. 【配件方案】每条是否带来源标注
3. 声称的槽位数与实列条数是否自洽
4. 槽位数与本地档案是否一致（配件改变槽位是合法的，但必须说明依据）
5. 档案填了 `red_lines` 的属性是否在【属性评估】里逐项检查

还支持**多张方案卡**：按【枪械】头切开后每张独立过检，问题带枪名前缀合并返回。

### 2. 参数兼容层：让"换个模型"不用改代码

不同模型对参数的容忍度不一样（`kimi-k2.6` 锁死 `temperature=1`；有的不接受 `reasoning_effort`；有的不接受 `stream_options`）。
`AIService._create()` 不写死任何模型，而是**解析 400 报错里点名的参数名、摘掉后重试**：

```python
except openai.BadRequestError as e:
    for param in ("temperature", "reasoning_effort", "stream_options"):
        if param in str(e) and param in kwargs:
            kwargs.pop(param)          # 报错点谁的名，就摘掉谁，再试
```

所以 `.env` 里换厂商、换型号，业务代码一行不动。

### 3. 条件检索：只在真的需要时才花钱

意图不是 `answer`/`multi`、或者不需要资料时，**完全不发起搜索**。
需要时，检索词优先用抽出来的枪名（`三角洲行动 M4A1 改枪`）而不是用户原话，聚焦得多。
另外后端会**强制** `answer` 意图必须有检索结果，模型偷懒会被打回重搜（`forced_research` 记进日志）。

### 4. 搜索层用「空对象模式」隔离第三方 API

`NullSearch` 永远返回空列表，于是**上层不需要写任何 `if 有搜索服务` 判断**——调了等于没调，系统自然降级成"纯模型经验 + 全部标未核实"。
换成博查或 Tavily 只改 `.env` 一行。搜索失败也**返回空列表而不抛异常**，不拖垮整条链路。

### 5. 历史增量压缩：越聊越长，但不能越聊越贵

对话超 14 条时，把旧消息滚动压成一份「前情提要」塞进 system。
关键是**只压上次没压过的那批**（`skip_first=summarized`）——不会每轮都重压一遍全部历史，这部分成本是可控的。

### 6. 可观测性：每个回答都留痕

每次请求都往 `request_logs` 写一行，包含：意图、槽位、是否检索、检索轮数、是否被强制重搜、质检问题清单、是否修复重试、prompt/completion tokens、意图耗时、总耗时、检索词、错误信息。

> 排查"为什么这回答得不好"，先看这张表 —— 是意图判错了？还是没搜到？还是质检反复打回？
> 这比在几百行日志里翻要快得多。

## 五、快速开始

```bash
pip install -r requirements.txt

cp .env.example .env      # 然后填入你自己的 LLM_API_KEY

python app.py             # 打开 http://127.0.0.1:5000
```

`.env` 里模型和搜索服务都是可插拔的（任何 OpenAI 兼容厂商）：

| 变量 | 说明 |
|---|---|
| `LLM_API_KEY` / `LLM_BASE_URL` / `LLM_MODEL` | 主模型（硅基流动 / DeepSeek / Kimi… 都行） |
| `ROUTER_API_KEY` / `ROUTER_BASE_URL` / `ROUTER_MODEL` | 意图判断用的便宜小模型；**留空则自动回退主模型** |
| `SEARCH_PROVIDER` | `none` / `bocha` / `tavily` / `kimi_builtin` |
| `SEARCH_API_KEY` | 搜索服务密钥（`none` 时不用填） |
| `SECRET_KEY` | Flask session 加密钥匙 |

健康检查：`GET /health` → `{"status": "healthy"}`

## 七、已知限制（诚实交代）

1. **`kimi_builtin`（模型内置搜索）在新模型上不可用** —— 实测 `kimi-k3` / `kimi-k2.6` 会报 `400 Invalid request: tokenization failed`，而 `kimi-k2.5` 时代是正常的。做了参数消融实验确认**不是参数或模型能力问题**，是内置搜索的结果回填格式不再兼容。
   当前默认 `SEARCH_PROVIDER=none`（整条流水线正常，只是少了实时资料）。
   **要恢复联网检索，推荐改用独立搜索服务**（`bocha` / `tavily`，适配器是现成的），而不是继续绑定厂商的内置工具。
2. **单机 SQLite + 本地 JSON** —— 没有并发控制，不适合多实例部署。
3. **枪械档案依赖人工整理** —— `tests/档案核查清单.md` 记录了核对进度，`red_lines` 字段尚未填满，对应的质检项因此处于未激活状态。
4. **测试集是手动的** —— 15 题需要人工跑，还没有接进 CI。
5. **只在单领域验证过** —— 意图/槽位/质检的规则都是为改枪场景写的，换领域要重写 prompt 和校验规则。
